# Roadmap World-Gen — что решено, что нет

Сводка состояния решений по системе после смены парадигмы (август 2026): от
«ДНК как контрастивный эмбеддинг» к «ДНК как структурированный 3D-латент +
состояние сцены». Документ-сверка: сюда смотрим перед тем, как что-то строить,
и сюда возвращаемся, когда решение принято.

## Легенда пометок

| Метка | Значение |
| ----- | -------- |
| `✅ утверждено` | Решено явно: либо требование заказчика, либо принятое и реализованное решение. Менять — через ADR. |
| `🟡 продумано` | Проработано и выглядит правильным, но явного утверждения не было. Можно строить на этом, помня, что это гипотеза. |

## 1. Требования и рамки продукта

| № | Пункт | Статус |
| - | ----- | ------ |
| 1.1 | Идентичность объектов и персонажей сохраняется между кадрами, ракурсами и сценами. Это главное требование, ради него строится всё остальное. | `✅ утверждено` |
| 1.2 | Объекты хранятся в базе и воспроизводятся в **нужном ракурсе и нужной позе** по запросу. | `✅ утверждено` |
| 1.3 | Сцена дополняется инкрементально: добавление объекта не пересоздаёт уже существующие и не ломает их состояние. | `✅ утверждено` |
| 1.4 | Физика взаимодействий (падение, контакт, разрушение) считается, а не рисуется «на глаз». | `✅ утверждено` |
| 1.5 | Один и тот же набор ассетов отдаётся в разных визуальных стилях: гиперреализм, комикс, манга и т.д. | `✅ утверждено` |
| 1.6 | Генерация **изображений** — первичная задача; видеоряд — производное от того же состояния. | `✅ утверждено` |
| 1.7 | Сцена — версионируемая структура с ветками под сюжетные линии («git сцены»). | `✅ утверждено` |
| 1.8 | 3D-сборка и симуляция исполняются на сервере, не на клиенте. | `✅ утверждено` |
| 1.9 | Real-time / playable — **не** в текущих рамках. Отложено до дистилляции. | `🟡 продумано` |
| 1.10 | Целевая аудитория и сценарий использования (кто и зачем строит миры) — на этом висит оценка «сколько ассетов нужно» и вся экономика. | `🔴 не решено` |

## 2. Представление объекта (ДНК)

| № | Пункт | Статус |
| - | ----- | ------ |
| 2.1 | ДНК — **структурированный 3D-латент**, декодируемый в геометрию (3DGS/меш), а не pooled-вектор. Причина: контрастив обучает различимость, а нужна достаточность для восстановления. | `🟡 продумано` |
| 2.2 | Идентичность **структурная**, а не статистическая: это буквально тот же ассет, декодированный заново. Только так «кадр 1 = кадр 100» держится по построению. | `🟡 продумано` |
| 2.3 | Паспорт объекта разложен на 4 независимых канала: геометрия · внешний вид · риг · физсвойства. Причина: поза, обгорание и разрушение обязаны меняться независимо друг от друга и от идентичности. | `🟡 продумано` |
| 2.4 | Контрастивный pooled-вектор сохраняется, но **понижается в роли** — становится ключом поиска в retrieval-индексе, а не представлением объекта. | `🟡 продумано` |
| 2.5 | На чём базируем структурированный латент: адаптировать готовую TRELLIS-линию, собирать своё, или третий вариант. **Блокирует почти всё остальное.** | `🔴 не решено` |
| 2.6 | Для **именованных** ассетов реконструкция по одной картинке в рантайме не нужна — ассет собирается офлайн, тщательно, один раз. Убирает самую ненадёжную часть из горячего пути. | `🟡 продумано` |
| 2.7 | Формат хранения латента, версионирование ассетов, миграции при смене модели-кодировщика (что делать со старой базой, если поменяли энкодер). | `🔴 не решено` |

## 3. Хранение и состояние сцены

| № | Пункт | Статус |
| - | ----- | ------ |
| 3.1 | Двухуровневое хранение: **неизменяемая библиотека ассетов** (канонические паспорта) + **изменяемое состояние сцены** (позы, повреждения, обломки, скорости). | `🟡 продумано` |
| 3.2 | Разделение **ассет против инстанса**: два одинаковых стула — один ассет, два инстанса со своими состояниями. | `🟡 продумано` |
| 3.3 | Результат симуляции **запекается и хранится**, а не пересчитывается при обращении к версии. Причина: симуляция не воспроизводится бит-в-бит между запусками, обломки лягут иначе, и уже показанный пользователю кадр перестанет совпадать. | `🟡 продумано` |
| 3.4 | Лог правок используется для истории и ветвления, но не как источник для пересчёта состояния. | `🟡 продумано` |
| 3.5 | Слой **сеттинга** над реестром: ограничивает поиск ассетов и задаёт стилевые дефолты мира. | `🟡 продумано` |
| 3.6 | Семантика ветвления: что значит «ветка сюжета», можно ли сливать ветки, что происходит при правке ассета, который уже использован в сотне сохранённых сцен. | `🔴 не решено` |
| 3.7 | Схема данных графа сцены (конкретный JSON): поля, связи, инварианты, валидация. | `🔴 не решено` |

## 4. Поиск и наполнение базы

| № | Пункт | Статус |
| - | ----- | ------ |
| 4.1 | **Именованный резолв и семантический поиск — разные операции.** «Персонаж N» разрешается только по идентификатору; ненайденный ID — ошибка, а не повод подобрать похожего. «Замок» без имени — семантический поиск с выбором. | `🟡 продумано` |
| 4.2 | Явный путь при промахе: генерируем ассет, регистрируем с новым ID, дальше он полноправный. Без этого любое новое существительное ломает пайплайн. | `🟡 продумано` |
| 4.3 | Стоимость подготовки одного ассета (реконструкция, риг, чистка, стилевые варианты) — **главная новая статья расходов**, не оценена. | `🔴 не решено` |
| 4.4 | Источники исходных 3D: Objaverse-XL как база, CO3D/MVImgNet для реализма, Rig-XL / Articulation-XL для риггинга. Лицензионная чистота под коммерческое использование не проверена. | `🔴 не решено` |
| 4.5 | Наполнение базы — **пользовательская загрузка референсов проекта**: пользователь даёт персонажа с разных ракурсов, по ним строится модель в стиле проекта. См. [ADR 0002](../architects/adr/0002-style-comes-from-project-assets.md). | `✅ утверждено` |
| 4.6 | Реконструкция по загруженным видам: качество, минимальное число ракурсов, что делать при противоречивых видах (см. 7.15). | `🔴 не решено` |
| 4.7 | Правовая сторона пользовательских загрузок (чужие персонажи в чужой интеллектуальной собственности) — продуктовый вопрос, не технический, но решать придётся. | `🔴 не решено` |

## 5. Физика и взаимодействия

| № | Пункт | Статус |
| - | ----- | ------ |
| 5.1 | Симуляция идёт **на том же представлении, что и рендер** (MPM на гауссианах-частицах) — без меширования, одно представление для физики и картинки. | `🟡 продумано` |
| 5.2 | Ручная реология «Этапа 2.5» из исходного предложения отменена — она давала правдоподобие без корректности. | `⚫ устарело` |
| 5.3 | Гибрид: латентный/быстрый солвер на рутине, настоящий солвер точечно на физически-критичных событиях. | `🟡 продумано` |
| 5.4 | **Хрупкое разрушение** (замок, разрушенный огнём) — открытая исследовательская проблема: нет хороших моделей brittle fracture на этом представлении, и внутренние текстуры на сколах никто не делает правдоподобно. | `🔴 не решено` |
| 5.5 | **Огонь как процесс** (горение → изменение материала → потеря прочности) — готового решения нет. Обход на первое время: скриптовое повреждение + правка канала внешнего вида. | `🔴 не решено` |
| 5.6 | Обход для 5.4 на старте: заранее заготовленные варианты разрушения ассета вместо симуляции каждый раз. Не проверено, достаточно ли это визуально. | `🟡 продумано` |
| 5.7 | Бюджет симуляции: сколько частиц, сколько секунд симуляции на кадр, что делать со сценами, где объектов сотни. | `🔴 не решено` |

## 6. Артикуляция и позы

| № | Пункт | Статус |
| - | ----- | ------ |
| 6.1 | Поза — отдельный канал (риг + углы суставов), геометрия при смене позы не пересобирается. | `🟡 продумано` |
| 6.2 | Авто-риггинг решается готовыми моделями (UniRig, MagicArticulate), но **надёжен на гуманоидах и ломается на нестандартной топологии** — фэнтези-существ придётся ригать руками. | `🔴 не решено` |
| 6.3 | Откуда берутся сами позы: из симуляции (упал), из библиотеки анимаций, из текста («держит в руках»), из позы-референса. Механика не определена. | `🔴 не решено` |
| 6.4 | Захваты и контакты (персонаж **держит** посох) — привязка объекта к кости, у исходного предложения это было Hard Binding. Как это выглядит в новой парадигме — не проработано. | `🔴 не решено` |

## 7. Рендер, стили, борьба с галлюцинациями

| № | Пункт | Статус |
| - | ----- | ------ |
| 7.1 | **Два уровня рендера**: превью (сплат-рендер, секунды, для подбора камеры и композиции) и финал (генератор, минуты). Без этого разделения каждая правка камеры стоит полного прогона генератора. | `🟡 продумано` |
| 7.2 | В генератор идёт **весь контрольный стек**, а не одна карта глубины: глубина, нормали, маски инстансов по ID, отрендеренный цвет. Только по глубине идентичность утечёт обратно через дорисовку. | `🟡 продумано` |
| 7.3 | Поводок генератора **структурный, а не скалярный**: содержание заперто (маски, геометрия, силуэты), подача свободна. Галлюцинация ≠ стилизация, мерить их одной шкалой нельзя. | `🟡 продумано` |
| 7.4 | **Стилизация выносится в рендер** (тун-шейдер, контуры, палитра) там, где это возможно — детерминированно и кадрово стабильно. Генератор доводит последнюю милю. | `🟡 продумано` |
| 7.5 | **Стиль определяется ассетами проекта, а не генератором.** Проект несёт профиль стиля; ассеты авторятся/реконструируются в нём. Герои рендерятся, а не перерисовываются. Генератор отвечает за сеттинг, фон, свет и доводку. См. [ADR 0002](../architects/adr/0002-style-comes-from-project-assets.md). | `✅ утверждено` |
| 7.6 | **NPR-рендер обязателен** (плоская заливка, контуры, палитра) — следствие 7.5: раз стиль в ассете, рендерер обязан его показать. | `✅ утверждено` |
| 7.7 | Стилевые варианты персонажа в базе **не нужны** — стиль есть свойство проекта, а не переключатель на объекте. Снимает кратное удорожание контента. | `✅ утверждено` |
| 7.12 | **Профиль стиля управляет обоими концами**: параметрами рендера героев и настройкой генератора для фона. Один источник правды, два потребителя — иначе герой и фон разъедутся. | `🟡 продумано` |
| 7.13 | **Пространственно неоднородный поводок**: короткий на героях (по маскам инстансов), длинный на фоне. Центральный механизм после 7.5. | `🟡 продумано` |
| 7.14 | **Связность героя и фона** — новый основной риск вместо снятых: рендер и генерация должны читаться как один мир, иначе кадр выглядит коллажем. | `🔴 не решено` |
| 7.15 | Стили, **жульничающие с геометрией** (аниме-причёска, лицо не в перспективе, глаза одного размера с любого ракурса), не сводятся в одну модель из противоречащих видов. Приём «3D-версии» или гибрид с перерисовкой лица — не решено. | `🔴 не решено` |
| 7.8 | **Проверяющий цикл** после генерации: детектор + VLM сверяют кадр с графом сцены (те ли объекты, столько ли, там ли); не сошлось — перегенерация. | `🟡 продумано` |
| 7.9 | Обусловливание диффузии остаётся мягким — гарантировать нельзя, можно только сузить и проверить постфактум. Это принимаемое ограничение, не баг. | `🟡 продумано` |
| 7.10 | Темпоральная консистентность видео: покадровый прогон даёт мерцание дорисованных деталей. Подход (видеомодель на всей последовательности против покадрового с коротким поводком) не выбран. | `🔴 не решено` |
| 7.11 | Какой генератор берём в проде (FLUX.2 klein 4B под Apache-2.0 против альтернатив) и на чём обучаем стилевые LoRA. | `🔴 не решено` |

## 14. Риски

| Риск | Почему серьёзен |
| ---- | --------------- |
| **Разрастание объёма** | Это система из шести подсистем вместо одной модели. Сейчас это риск №1 — больший, чем любой технический. |
| Нерешённое разрушение | Сценарий «замок, разрушенный огнём» упирается в открытую исследовательскую проблему (5.4), а он в требованиях. |
| Стоимость ассетов | Если подготовка одного ассета дорога, продукт не масштабируется, а мы этого пока не знаем (4.3). |
| Два противоречащих плана | Старый runbook и новая парадигма сосуществуют — источник неверных решений, пока раздел 11 не закрыт. |
| Мягкость обусловливания | Гарантий от диффузии нет; проверяющий цикл обязателен, а он ещё не спроектирован (7.8). |
| Риггинг нестандартных существ | Ручная работа там, где ожидалась автоматика (6.2). |

## 15. Предлагаемая последовательность

Не утверждена — это моя рекомендация, обсуждаемая.

1. **Закрыть 2.5** (на чём базируем латент) — блокирует почти всё.
2. **Тонкий вертикальный срез**: один ассет → декод → поза → рендер → генератор.
   Без физики, без хранилища, без стилей. Цель — доказать сквозное сохранение
   идентичности на реальном ассете. Пока этого нет, всё остальное — гипотеза.
3. **Хранилище сцены и инкрементальные правки** — это продуктовое отличие,
   и оно важнее физики: сценарий с посохом ломается без персистентности, а не
   без корректной физики.
4. **Стилевые тиры** — начиная с шейдерного, как самого дешёвого и стабильного.
5. **Проверяющий цикл** — дёшев и ловит регрессии рано; можно и раньше пункта 4.
6. **Физика** — последней из основного, как самая рискованная и с открытыми дырами.

Главный принцип: сначала тонкий сквозной срез, потом утолщение. Система такого
размера не собирается «по подсистеме за раз» — иначе интеграционные проблемы
всплывут в самом конце.

## 16. Ближайшие решения, которые нужно принять

1. `2.5` — база структурированного латента (и связанное `13.1` — не берём ли вместо этого игровой движок).
2. `11.2`–`11.4` — что делаем со старым планом: переписываем фазы или помечаем как заменённый.
3. `4.5` + `4.3` — кто наполняет базу ассетами и сколько это стоит.
4. `1.10` — для кого продукт; без этого нельзя оценить ни объём базы, ни экономику.
