# Подробный план реализации: консистентная и физически‑правдоподобная генерация сцен

> Инженерный runbook. Каждая фаза разбита на конкретные шаги, у **каждого шага** есть измеримая проверка и ветка «если не прошло». Идём **фото → видео**, консистентность (ось A) раньше физики (ось B). Каждая фаза открывается только пройдя свой go/no‑go.

---

## Как читать этот документ

- **Ось A** — консистентность идентичности (тот же объект между кадрами/ракурсами/ассетами).
- **Ось B** — физическая правдоподобность (динамика, столкновения, деформации).
- **Архитектурный принцип:** персистентное объектно‑центричное **латентное состояние мира** (держит A) + **латентный физдвижок** — дистиллят настоящего солвера (держит B) + **замороженный генератор** как рендер (фото = 1 рендер, видео = рендер прокатанного состояния).
- Формат шага: **Действия** (что сделать) → **Проверка ✅** (как убедиться, что шаг закрыт) → **Если не прошло** (куда копать).
- `❄` заморожено · `🔥` обучаемое · `⊙` офлайн (только на этапе подготовки данных/учителя).

### Обозначения статуса шага
`[ ]` не начато · `[~]` в работе · `[x]` закрыто по «Проверке».

## Общий стек и предпосылки

**Модели‑бэкбоны (открытые):**
- Признаки/идентичность: `DINOv3` (или DINOv2) — `❄`.
- Генератор изображений: `FLUX.2 [klein] 4B` (Apache‑2.0) или `SDXL` (самая зрелая экосистема адаптеров) — `❄` (+LoRA при необходимости).
- Генератор видео: `LTX‑Video` (дёшево, влезает в 12 ГБ) → позже `Wan 2.2` (качество) — `❄`(+LoRA).
- Feed‑forward 3D: `AnySplat` / `LRM` / `TriplaneGaussian` / `FluSplat`.
- Физика‑учитель: `Genesis` (быстрый дифф‑солвер) и/или логи `PhysX` из `Unreal Engine 5` — `⊙`.
- Сегментация инстансов для данных: `SAM` — `⊙`.

**Обучаемое (мелкое):** ДНК‑компрессор (Slot Attention / Perceiver‑ресемплер), инъектор в стиле IP‑Adapter (доп. K/V/out кросс‑внимания), латентный физ‑переход `fθ` (GNS‑стиль), адаптеры раскладки.

**Инфраструктура:** PyTorch, `diffusers`, `PEFT`/LoRA, `accelerate`, `xformers`; `FAISS` (retrieval‑банк); `wandb`/`mlflow` (трекинг экспериментов); `RAFT`/оптический поток (темпоральные метрики); DVC/`git‑lfs` (версии данных и весов).

**Железо (ориентир):** фазы 0–3 — 1× 24 ГБ GPU (RTX 4090 / A100); фазы 4–5 — 1–4 GPU; фаза 6 — по потребности.

**Предпосылки готовности (Definition of Ready):**
- [ ] Репозиторий с фиксированными seed, конфигами (Hydra/YAML) и трекингом экспериментов.
- [ ] Скрипт воспроизводимости: один конфиг → один прогон → залогированные метрики.
- [ ] Держатель «золотого набора» из 20–50 объектов и 8‑ракурсных рендеров для регресс‑проверок (не участвует в обучении).

## Дорожная карта (обзор)

| Фаза | Название | Ось | Модальность | Главный go/no‑go |
|---|---|---|---|---|
| 0 | База и метрики | измерение | фото+видео | метрики воспроизводимы, зазор виден |
| 1 | View‑invariant «ДНК» одного объекта | A | фото | ДНК > IP‑Adapter по кросс‑виду |
| 2 | Мультиассетная сцена + retrieval | A | фото | нет утечки идентичности при K объектов |
| 3 | Персистентное 3D‑нативное состояние | A(+геом) | мост | виды сходятся к одному объекту |
| 4 | Латентный физдвижок | B | видео | совпадение с солвером в пределах ε, ≥10× |
| 5 | Интеграция: полный нейродвижок | A+B | фото+видео | пороги обеих осей на обеих модальностях |
| 6 | Масштаб / real‑time | — | фото+видео | целевой FPS при удержании качества |

## Фаза 0 — База и метрики

**Цель:** до любой разработки — настроить измерение и замерить потолок готовых решений.
**Гипотеза H0:** готовые методы дают недостаточную консистентность/физику; зазор измерим и воспроизводим.
**Вход:** золотой набор объектов/сцен. **Выход:** зафиксированный пайплайн метрик + бейзлайн‑числа.

### Шаги

#### 0.1 Собрать оценочный набор `[ ]`
**Действия:**
- [ ] Отобрать 20–50 объектов (жёсткие, деформируемые, с мелкой фактурой/текстом) и 8 ракурсов/контекстов на каждый.
- [ ] Отобрать 10–15 мультиобъектных сцен и 5–10 «физических» сюжетов (падение, стопка, драпировка, погружение).
- [ ] Зафиксировать набор как read‑only, версионировать (DVC).

**Проверка ✅:** `dvc status` чист; хеш набора записан в конфиг; набор не пересекается с любыми обучающими источниками (скрипт проверки пересечений по перцептивному хешу возвращает 0 коллизий).
**Если не прошло:** есть пересечение с train → заменить объекты; набор мал → добить до нижней границы (20 объектов / 5 физ‑сюжетов).

#### 0.2 Реализовать метрики оси A `[ ]`
**Действия:**
- [ ] Идентичность между видами: косинус `DINO`‑эмбеддингов кропа объекта + `CLIP‑I` (subject fidelity).
- [ ] Темпоральная (для видео): warping‑error по оптическому потоку (`RAFT`) между соседними кадрами + `CLIP` frame‑to‑frame.
- [ ] Качество/промпт: `FID`/`FDD` и `CLIPScore` — как «предохранители» от деградации.

**Проверка ✅:** на паре «идентичные картинки» метрика идентичности ≈ максимум, на «явно разных» — низкая; ранжирование совпадает с ручной разметкой на 10 контрольных парах (Spearman ≥ 0.8).
**Если не прошло:** метрика не различает — сменить кроп/нормализацию признаков; проверить, что сравниваем один и тот же инстанс (через маску SAM).

#### 0.3 Подключить бенчмарки оси B `[ ]`
**Действия:**
- [ ] Встроить прогон по `PhyWorldBench` / `T2VPhysBench` (физ‑реализм text‑to‑video) и `Physion‑Eval` (человеко‑ориентированная оценка правдоподобия).
- [ ] Определить 3–5 автоматических физ‑чеков (непроникновение, сохранение объёма/массы объекта, направление гравитации) на своих сюжетах.

**Проверка ✅:** бенчмарк отдаёт число на 1 тест‑видео за < N минут; синтетический «идеальный» ролик из симулятора получает высокий физ‑скор, «сломанный» (объект проходит сквозь пол) — низкий.
**Если не прошло:** бенчмарк не ставится локально — начать с собственных 3 физ‑чеков и человеческой оценки, бенчмарк подключить позже.

#### 0.4 Замерить бейзлайны из коробки `[ ]`
**Действия:**
- [ ] Фото: `IP‑Adapter` / `InstantID` на золотом наборе.
- [ ] Видео: reference/first‑frame режим `LTX‑Video` (и `Wan 2.2`, если есть железо).
- [ ] Залогировать все метрики как «baseline v0».

**Проверка ✅:** таблица бейзлайнов в трекере; повторный прогон того же конфига даёт метрики в пределах ±1–2% (воспроизводимость).
**Если не прошло:** разброс велик — зафиксировать seed, число шагов сэмплера, версии весов; усреднить по ≥3 прогонам.

### 🚦 Go/No‑Go фазы 0
- [ ] Все метрики (A и B) воспроизводимы (±2%) и задокументированы.
- [ ] Виден измеримый зазор бейзлайна до «идеала» хотя бы по одной оси.
**Артефакты:** `eval/` (набор + скрипты метрик), таблица `baseline_v0`.

## Фаза 1 — View‑invariant «ДНК» одного объекта (фото)

**Цель:** устойчивая идентичность объекта между ракурсами при почти нулевой доп‑стоимости.
**Гипотеза H1:** явная view‑invariant ДНК‑обусловленность превосходит наивный IP‑Adapter по кросс‑видовой идентичности без просадки качества/промпта.
**Вход:** метрики фазы 0. **Выход:** обученный ДНК‑компрессор + инъектор к замороженному генератору.

### Шаги

#### 1.1 Мультивид‑данные для инвариантности `[ ]`
**Действия:**
- [ ] `⊙` Рендер Objaverse/Objaverse‑XL: по 8–24 вида на объект (только рендерер, не физдвижок).
- [ ] Добавить реальный мультивид: `CO3D`, `MVImgNet`; для видео‑источников — вырезать один инстанс через `SAM`.
- [ ] Сформировать пары «тот же объект, другой вид» (позитивы) и «другой объект» (негативы).

**Проверка ✅:** случайная выборка 50 пар вручную верна (позитив = тот же объект) ≥ 96%; распределение ракурсов покрывает полусферу (гистограмма углов без больших дыр).
**Если не прошло:** много ложных позитивов — ужесточить трекинг инстанса; дыры по ракурсам — досэмплировать рендеры.

#### 1.2 ДНК‑компрессор поверх замороженного энкодера `[ ]`
**Действия:**
- [ ] `❄` Прогнать кроп объекта через `DINOv3` → плотные признаки.
- [ ] `🔥` Сжать в `N=4…16` токенов ресемплером (Slot Attention / Perceiver) = «ДНК».
- [ ] Лосс: денойзинг‑реконструкция (условие на ДНК) + **контрастив** на инвариантность (позитивы близко, негативы далеко).

**Проверка ✅:** кросс‑видовая близость ДНК (позитивы) − близость к негативам ≥ заданного зазора; линейный probe по ДНК различает объекты из held‑out с точностью ≥ порога (напр. top‑1 ≥ 0.7 на 50 классах).
**Если не прошло:** ДНК путает объекты → поднять вес контрастива / число токенов; ДНК запоминает позу → добавить аугментации позы/света в позитивы.

#### 1.3 Инъекция ДНК в замороженный генератор `[ ]`
**Действия:**
- [ ] `🔥` IP‑Adapter‑стиль: доп. K/V/out кросс‑внимания под ДНК‑токены в `❄`FLUX.2/SDXL.
- [ ] Обучать **только** инъектор + ресемплер; генератор заморожен.
- [ ] Подобрать силу условия λ (скан 2–3 значений).

**Проверка ✅:** при фиксированном промпте и разных сидax объект узнаваем (DINO/CLIP‑I идентичность ≥ порога), при этом `FID`/`CLIPScore` не хуже бейзлайна более чем на δ.
**Если не прошло:** объект «размывается» → выше λ / больше токенов; промпт перестаёт слушаться → ниже λ / регуляризация на текстовое внимание.

#### 1.4 Сравнение с бейзлайном и абляции `[ ]`
**Действия:**
- [ ] Прогнать: (а) чистый текст, (б) IP‑Adapter, (в) наша ДНК — на золотом наборе, 8 видов.
- [ ] Абляции: с/без контрастива; `N=1` vs `N` токенов; заморозка vs лёгкий тюн энкодера.

**Проверка ✅ (гейт‑критерий H1):** ДНК‑консистентность (DINO/CLIP‑I по видам) **заметно выше** IP‑Adapter (напр. +0.05 и статзначимо на бутстрэпе) при не‑ухудшении FID/промпта.
**Если не прошло:** ДНК ≈ IP‑Adapter → значит выигрыш даёт не архитектура, а данные: усилить мультивид/контрастив или признать, что для фото достаточно IP‑Adapter, и перенести акцент на фазу 3 (3D‑состояние).

### 🚦 Go/No‑Go фазы 1
- [ ] H1 подтверждён (ДНК > IP‑Adapter, без регрессий) при < N GPU‑часов.
- [ ] Абляции показывают, какой компонент даёт выигрыш (для переноса дальше).
**Артефакты:** `dna_encoder/` (веса ресемплера+инъектора), отчёт абляций, таблица `phase1`.

## Фаза 2 — Мультиассетная сцена + retrieval (фото)

**Цель:** собрать сцену из многих ассетов без смешивания идентичностей; безграничная библиотека ассетов.
**Гипотеза H2:** несколько ДНК + раскладка композируются без утечки атрибутов; retrieval даёт масштаб по ассетам без переобучения.
**Вход:** ДНК‑стек фазы 1. **Выход:** мультиобъектный конвейер + банк ассетов.

### Шаги

#### 2.1 Раскладка сцены как условие `[ ]`
**Действия:**
- [ ] Ввести раскладку: боксы/грубый граф отношений (кто где, кто на чём).
- [ ] `🔥` Регионально‑маскированное внимание: каждая группа ДНК‑токенов «привязана» к своему боксу (GLIGEN‑стиль).

**Проверка ✅:** объект появляется в заданном боксе (IoU центроида детекции с целевым боксом ≥ 0.6 на 90% случаев).
**Если не прошло:** объекты «плывут» из боксов — усилить маскирование/позиционные эмбеддинги; конфликтующие боксы — валидатор раскладки перед генерацией.

#### 2.2 Композиция K ДНК без утечки `[ ]`
**Действия:**
- [ ] Инъектировать 2→K ДНК одновременно с масками.
- [ ] Обучать/тюнить только адаптер раскладки; проверять на растущем K.

**Проверка ✅ (гейт‑критерий H2):** утечка атрибутов < P% (детектор + VLM‑VQA: «это тот же объект? сколько их? не смешаны ли текстуры?») на сценах из 2–4 объектов; мульти‑субъект‑консистентность в духе `CogCanvas`/`PSR` не ниже порога.
**Если не прошло:** текстура A перетекает на B → сильнее развязать внимание по маскам; растёт K → деградация → ограничить K на кадр и строить сцену итеративно (инпейнт по одному).

#### 2.3 Retrieval‑банк ассетов `[ ]`
**Действия:**
- [ ] Считать ДНК всех ассетов библиотеки, положить в `FAISS`‑индекс (ID → ДНК).
- [ ] При генерации — доставать ДНК по ID/запросу и обусловливать (без обучения на новый ассет).

**Проверка ✅:** добавление нового ассета = одна вставка в индекс; сгенерированный объект по извлечённой ДНК идентичен эталону (CLIP‑I ≥ порога) без какого‑либо дообучения.
**Если не прошло:** извлечённая ДНК даёт непохожий объект → проверить нормализацию/метрику индекса; коллизии близких ассетов → увеличить размер ДНК/добавить текстовый тег.

#### 2.4 Регресс‑прогон фото‑пайплайна `[ ]`
**Действия:**
- [ ] Прогнать все мультиобъектные сцены золотого набора; сравнить с фазой 1 и бейзлайном.

**Проверка ✅:** метрики не хуже фазы 1 на одиночных объектах (нет регресса) и лучше бейзлайна на мультиобъектных.
**Если не прошло:** регресс на одиночных — раскладочный адаптер вмешивается в простой случай → включать его только при ≥2 ДНК.

### 🚦 Go/No‑Go фазы 2
- [ ] H2 подтверждён: сцена из K объектов без утечки, добавление ассета без обучения.
**Артефакты:** `layout_adapter/`, `asset_bank/` (FAISS), таблица `phase2`.

## Фаза 3 — Персистентное 3D‑нативное состояние (мост фото → видео)

**Цель:** консистентность по ракурсу и во времени как **свойство представления**, а не удача генерации.
**Гипотеза H3:** «структурированная ДНК» (3D‑нативное состояние объекта) даёт кросс‑видовую и темпоральную стабильность из коробки.
**Вход:** ДНК‑стек фаз 1–2. **Выход:** состояние объекта, из которого рендерится любой вид/кадр.

### Шаги

#### 3.1 Feed‑forward построение состояния `[ ]`
**Действия:**
- [ ] Взять `AnySplat`/`LRM`/`TriplaneGaussian`/`FluSplat`: из 1–few видов ассета → 3D‑нативный код (tri‑plane / feature‑field / мини‑сплат) за один проход, **без пер‑сценовой оптимизации**.
- [ ] Связать код с ID ассета (расширение «ДНК» до «структурированной ДНК»).

**Проверка ✅:** построение состояния для нового ассета за один forward (< секунд), без цикла оптимизации; время не растёт с числом ассетов сверх линейного.
**Если не прошло:** качество feed‑forward низкое на редких ракурсах — доснять входные виды (2–4) или добавить лёгкий 1‑проходный рефайн; НЕ скатываться в полную пер‑сценовую оптимизацию.

#### 3.2 Рендер произвольного вида/кадра `[ ]`
**Действия:**
- [ ] Рендерить состояние в 2D (сплат‑рендер или замороженный генератор, обусловленный проекцией состояния).
- [ ] Прогнать орбиту камеры вокруг объекта (например, 36 видов).

**Проверка ✅:** геометрическая стабильность — при подаче сгенерированных видов обратно в feed‑forward 3D разброс формы низкий (дисперсия ключевых метрик формы ≤ порога); силуэт/глубина согласованы между соседними видами (нет «скачков»).
**Если не прошло:** объект «дышит»/меняет форму по орбите — усилить 3D‑код (ёмкость tri‑plane), добавить мультивид‑лосс согласованности между соседними видами.

#### 3.3 Темпоральная согласованность (мост в видео) `[ ]`
**Действия:**
- [ ] Зафиксировать состояние, менять только камеру/позу между кадрами → короткий клип «облёта».
- [ ] Замерить темпоральные метрики (warp‑error, CLIP frame‑to‑frame).

**Проверка ✅ (гейт‑критерий H3):** темпоральный дрейф идентичности существенно ниже, чем у пиксельного reference‑видео (фаза 0) на тех же облётах; переход фото→видео не ломает идентичность.
**Если не прошло:** дрейф всё ещё высок — значит рендер добавляет отсебятину: сильнее привязать рендер к состоянию (снизить свободу генератора) или перейти на прямой сплат‑рендер для геометрии + генератор только для стиля.

#### 3.4 Мультиобъектная сцена в состоянии `[ ]`
**Действия:**
- [ ] Разместить несколько объектных состояний в общей сцене по раскладке фазы 2 (общая камера/свет).

**Проверка ✅:** окклюзии и относительные глубины корректны (проверка по карте глубины); идентичности не смешиваются при движении камеры.
**Если не прошло:** конфликты глубины/окклюзии — ввести общий буфер глубины сцены и сортировку состояний.

### 🚦 Go/No‑Go фазы 3
- [ ] Виды сходятся к одному объекту (низкий разброс формы), переход фото→видео держит идентичность, построение состояния — feed‑forward.
**Артефакты:** `state_builder/`, датасет состояний, таблица `phase3`.

## Фаза 4 — Латентный физдвижок (динамика, видео)

**Цель:** прокатывать состояние во времени физически‑правдоподобно, обобщая на новые конфигурации, при ≥ 10× скорости солвера.
**Гипотеза H4:** латентный переход, дистиллированный из настоящего солвера, точнее ручной реологии и дешевле пиксельной видеомодели.
**Вход:** состояние фазы 3. **Выход:** обученный переход `fθ`, прокатывающий состояние.

### Шаги

#### 4.1 Данные‑учитель из солвера `[ ]`
**Действия:**
- [ ] `⊙` Выбрать 1–2 класса взаимодействия для старта (падение/стопка кубиков; драпировка ткани).
- [ ] `⊙` Сгенерировать роллауты в `Genesis` (быстро, дифференцируемо) и/или логи `PhysX` из UE5: состояния объектов по времени + контакты/силы.
- [ ] Сопоставить объекты сцены с узлами графа состояния.

**Проверка ✅:** роллауты детерминированно воспроизводимы (тот же seed → та же траектория); хватает разнообразия (гистограмма начальных конфигураций без дыр); held‑out‑набор роллаутов отложен.
**Если не прошло:** мало разнообразия → расширить рандомизацию начальных условий/материалов; солвер медленный → уменьшить сложность сцены на старте.

#### 4.2 Латентный переход `fθ` с индуктивными смещениями `[ ]`
**Действия:**
- [ ] `🔥` Состояние = граф (узлы = объектные латенты + физ‑атрибуты: масса, жёсткость, трение; рёбра = контакты/связи).
- [ ] `🔥` Переход = message passing (GNS‑стиль) с **локальностью**; добавить **эквивариантность** (сдвиг/поворот) и/или **законы сохранения** (энергия/импульс).
- [ ] Обучение авторегрессией с **pushforward‑noise** (учим на собственных ошибках роллаута).

**Проверка ✅:** ошибка одного шага `‖fθ(s_t) − solver(s_t)‖` ниже порога на held‑out; латентный шаг ≥ 10× быстрее шага солвера (замер времени).
**Если не прошло:** одношаговая ошибка велика — увеличить ёмкость/итерации message passing; медленно — уменьшить размер латента/число итераций.

#### 4.3 Стабильность длинного роллаута `[ ]`
**Действия:**
- [ ] Прокатить `fθ` на длинных горизонтах (в разы длиннее обучающих окон).
- [ ] При дрейфе включить меры: pushforward‑noise, PDE‑refiner, периодическую коррекцию настоящим солвером раз в K шагов.

**Проверка ✅:** накопленная ошибка на горизонте H растёт суб‑линейно и остаётся ниже порога; энергия/импульс не «взрываются» (метрики сохранения в коридоре).
**Если не прошло:** роллаут расходится — усилить сохранение/refiner; как временную опору — гибрид с коррекцией солвером (переходим к «страховке» фазы 5).

#### 4.4 Обобщение на новые конфигурации `[ ]`
**Действия:**
- [ ] Тест на **невиданном** числе/расстановке объектов, новых массах/материалах в пределах домена.

**Проверка ✅ (гейт‑критерий H4, часть 1):** физ‑ошибка на новых конфигурациях не сильно выше, чем на трейне (обобщение есть); заметно лучше ручной реологии (World‑Gen 2.5) как бейзлайна.
**Если не прошло:** нет обобщения — усилить эквивариантность/локальность, расширить домен данных‑учителя.

#### 4.5 Рендер динамики и физ‑валидация `[ ]`
**Действия:**
- [ ] Рендерить прокатанное состояние в видео (замороженный генератор/сплат).
- [ ] Прогнать `PhyWorldBench`/`T2VPhysBench`/`Physion‑Eval` + собственные физ‑чеки.
- [ ] Сравнить с пиксельной видеомоделью (фаза 0) и с ручной реологией.

**Проверка ✅ (гейт‑критерий H4, часть 2):** физ‑скор рендера ≥ пиксельной видеомодели и ≥ ручной реологии; непроникновение/гравитация проходят на ≥ порога % сюжетов.
**Если не прошло:** рендер портит физику, хотя состояние верное — рассинхрон рендера и состояния → жёстче привязать рендер к геометрии состояния.

### 🚦 Go/No‑Go фазы 4
- [ ] Совпадение с солвером в пределах ε, ≥ 10× скорости, обобщение на новые конфиги, физ‑скор ≥ бейзлайнов.
**Артефакты:** `physics_engine/` (веса `fθ`), teacher‑датасет, таблица `phase4`.

## Фаза 5 — Интеграция: полный нейродвижок (фото + видео)

**Цель:** единая система — консистентная физически‑правдоподобная сцена и в фото‑серии, и в видео.
**Гипотеза H5:** слои 2 + 3 + 4 совместно дают консистентность и физику лучше любой части по отдельности.
**Вход:** артефакты фаз 2–4. **Выход:** сквозной пайплайн + гибрид со страховкой‑солвером.

### Шаги

#### 5.1 Сшивка конвейера `[ ]`
**Действия:**
- [ ] Собрать поток: ассеты → состояние (ф.3) → `fθ` (ф.4) → рендер; мультиассет по раскладке (ф.2) + retrieval (банк).
- [ ] Единый формат состояния и контракты интерфейсов между модулями.

**Проверка ✅:** сквозной прогон одного сюжета проходит без ручного вмешательства между стадиями; каждый интерфейс валидируется схемой (падение на неверном контракте, а не молчаливая ошибка).
**Если не прошло:** рассогласование форматов между модулями → зафиксировать типизированные контракты, добавить конвертеры на стыках.

#### 5.2 Physics‑guidance для критичных кадров `[ ]`
**Действия:**
- [ ] Встроить дифф‑физику/дифф‑рендер как ограничение на сэмплинге (штраф непроникновения/сохранения); опционально дообучение в духе `PhysCorr` (DPO на физ‑награду).
- [ ] Включать guidance выборочно (детектор «физически‑критичного» события).

**Проверка ✅:** на сюжетах, где базовый рендер нарушал физику, guidance снижает долю нарушений (метрика непроникновения) без заметной просадки качества.
**Если не прошло:** guidance роняет качество/скорость — снизить вес/частоту, применять только к кадрам контакта.

#### 5.3 Гибрид со страховкой‑солвером `[ ]`
**Действия:**
- [ ] Для физически‑точных событий (разрушение, точный контакт) — реальный солвер считает траекторию, `fθ` и рендер её «одевают».
- [ ] Определить политику переключения learned ↔ solver (по типу события/бюджету).

**Проверка ✅:** на «точных» сюжетах гибрид достигает физ‑скора солвера, оставаясь быстрее полного солвера по остальным кадрам (замер средней скорости на смешанном сюжете).
**Если не прошло:** переключение дёргается/видны швы — сглаживать переходы состояния, калибровать порог детектора события.

#### 5.4 Сквозная валидация на обеих модальностях `[ ]`
**Действия:**
- [ ] Фото‑серии: консистентность идентичности по видам/сценам (ось A) + качество.
- [ ] Видео: темпоральная консистентность + физ‑бенчмарки (ось B).
- [ ] Человеческая оценка (A/B «тот же объект?»/«похоже на реальную физику?»).

**Проверка ✅ (гейт‑критерий H5):** обе оси проходят пороги **на обеих модальностях**; ансамбль ≥ каждой отдельной части фаз 2/3/4; человеко‑оценка выше бейзлайна статзначимо.
**Если не прошло:** одна ось тянет вниз — вернуться в соответствующую фазу (A→ф.2/3, B→ф.4) точечно, не переделывая всё.

### 🚦 Go/No‑Go фазы 5
- [ ] Обе оси проходят пороги на фото и видео; гибрид даёт корректность на точных сюжетах.
**Артефакты:** `pipeline/` (сквозной), политика гибрида, отчёт человеко‑оценки, таблица `phase5`.

## Фаза 6 — Масштаб и real‑time (опционально)

**Цель:** playable/real‑time и удешевление инференса.
**Гипотеза H6:** модульный конвейер можно дистиллировать в одну быструю студенческую модель без потери качества.
**Вход:** конвейер фазы 5 как учитель. **Выход:** быстрый студент + предобучение на масштабе.

### Шаги

#### 6.1 Дистилляция конвейера в быстрый студент `[ ]`
**Действия:**
- [ ] Генерировать пары «вход → выход» полным конвейером (учитель), обучить компактную end‑to‑end модель (в духе Genie/Oasis) имитировать его.

**Проверка ✅:** студент воспроизводит выход учителя (перцептивно + метрики) в пределах δ при кратно меньшей задержке.
**Если не прошло:** велика потеря качества — увеличить студента/объём дистилляционных данных или дистиллировать только «горячий путь» (интерактивные кадры).

#### 6.2 Self‑supervised предобучение в пространстве признаков `[ ]`
**Действия:**
- [ ] Предобучить состояние/динамику на **сыром видео** предсказанием в латенте признаков (`V‑JEPA 2`/`DINO‑WM` подход), затем дообучить на конвейерных данных.

**Проверка ✅:** предобучение улучшает дата‑эффективность (та же метрика достигается меньшим числом размеченных/симулированных примеров).
**Если не прошло:** нет выигрыша — представление признаков не марковское для динамики → сменить пространство (объектное вместо глобального).

#### 6.3 Real‑time бюджет `[ ]`
**Действия:**
- [ ] Профилировать задержку по стадиям; квантизация/дистилляция узких мест; целевой FPS.

**Проверка ✅ (гейт‑критерий H6):** целевой FPS достигнут при удержании качества относительно учителя в пределах δ.
**Если не прошло:** не хватает FPS — резать разрешение/горизонт, выносить рендер на сплат, кэшировать состояние между кадрами.

### 🚦 Go/No‑Go фазы 6
- [ ] Целевой FPS при приемлемой просадке качества; студент разворачивается автономно.
**Артефакты:** `student_model/`, отчёт по задержке, таблица `phase6`.

## Сквозные практики (проверять постоянно)

- **Регрессии:** после каждой фазы прогонять золотой набор всех предыдущих фаз; метрики не должны падать (регресс‑гейт в CI).
- **Воспроизводимость:** один конфиг → один прогон → залогированные метрики; фиксировать seed, версии весов, число шагов сэмплера.
- **Разделение осей:** никогда не смешивать метрики A и B в одном числе — отдельные пороги, отдельные отчёты.
- **Честный бейзлайн:** в каждой фазе держать «дешёвый» бейзлайн (IP‑Adapter, ручная реология, пиксельное видео), чтобы видеть реальный прирост.
- **Журнал решений (decision log):** каждый пройденный/непройденный гейт с числами и выводом — чтобы «почему свернули сюда» было прослеживаемо.
- **Данные:** версионировать (DVC), проверять на пересечение train/eval по перцептивному хешу.

### Реестр рисков и триггеры
| Риск | Триггер (когда бить тревогу) | Мера |
|---|---|---|
| Дрейф роллаута | ошибка на горизонте растёт супер‑линейно | pushforward‑noise, refiner, сохранение, коррекция солвером |
| Неверный латент | динамика не марковская / плохое обобщение | объектное состояние + отдельное поле для сред |
| Корректность ≠ правдоподобие | физ‑скор высок, но реальные контакты неверны | гибрид со страховкой‑солвером на точных сюжетах |
| OOD‑материалы | резкий рост ошибки вне домена | эквивариантность/сохранение, расширение данных‑учителя |
| Утечка атрибутов | VLM‑VQA фиксирует смешение при K↑ | маскированное внимание, итеративная сборка сцены |
| Real‑time × модульность | задержка кратно выше бюджета | дистилляция в студента (ф.6) |

## Приложение A — Метрики: что и как считать
- **Идентичность (ось A):** косинус эмбеддингов `DINO` кропа объекта (по маске SAM) между парами видов; `CLIP‑I` как второй голос. ↑ лучше.
- **Темпоральная (ось A, видео):** warping‑error по потоку (`RAFT`) между соседними кадрами; `CLIP` frame‑to‑frame. ↓ лучше.
- **Геометрия (ось A, мультивид):** разброс метрик формы при подаче сгенерированных видов в feed‑forward 3D (`LRM`/`TriplaneGaussian`). ↓ лучше.
- **Мульти‑субъект (ось A):** протоколы `CogCanvas`/`PSR`; VLM‑VQA на счёт/связывание атрибутов.
- **Физика (ось B):** `PhyWorldBench`, `T2VPhysBench`, `Physion‑Eval` + собственные чеки (непроникновение, сохранение массы/объёма, гравитация).
- **Качество/промпт (предохранители):** `FID`/`FDD`, `CLIPScore`.

## Приложение B — Датасеты и источники
- Мультивид объектов: `Objaverse`/`Objaverse‑XL` (рендеры), `CO3D`, `MVImgNet`.
- Инстансы из видео: сегментация `SAM` + трекинг.
- Физика‑учитель: `Genesis` (роллауты), `Unreal Engine 5` + `PhysX` логи; пайплайны типа `SegGen` для мультимодальной разметки.

## Приложение C — Ключевые репозитории/модели и зачем
- `DINOv3`/`DINOv2` — плотные признаки, «ДНК», метрики идентичности.
- `FLUX.2 [klein]` / `SDXL` — генератор изображений (замороженный + инъектор).
- `IP‑Adapter` — референсная инъекция (и бейзлайн).
- `AnySplat`/`LRM`/`TriplaneGaussian`/`FluSplat` — feed‑forward 3D‑состояние.
- `GNS`/`MeshGraphNets` — архитектура латентного перехода `fθ`.
- `Genesis` — быстрый дифф‑солвер (учитель + страховка).
- `PhysGaussian` — физика на 3D‑сплатах (референс подхода «физика на нейро‑3D»).
- `LTX‑Video`/`Wan 2.2` — видеорендер и бейзлайны.
- `V‑JEPA 2`/`DINO‑WM` — self‑supervised предобучение динамики в латенте.
- `PhyWorldBench`/`T2VPhysBench`/`Physion‑Eval` — бенчмарки физики; `CogCanvas`/`PSR` — мульти‑субъект‑консистентность.
