# Roadmap MVP — первый сквозной срез

Тонкая полоска через все слои системы: один подготовленный 3D-персонаж →
рендер → генератор → красивая картинка в четырёх стилях, с сохранением
идентичности. Каждый слой реализован грубо; цель — не функциональность, а
**информация**: работает ли посылка продукта вообще.

- **Создан:** 2026-08-13
- **Контекст:** принцип из [Roadmap, раздел 15](Roadmap.md#15-предлагаемая-последовательность).
  Общее состояние решений — в [Roadmap.md](Roadmap.md).
- **Формат выхода:** только изображения. Видео вне рамок MVP.

---

## 1. Гипотеза, которую проверяем

> Один и тот же персонаж, взятый из подготовленного 3D-ассета, остаётся
> узнаваемо тем же самым в разных ракурсах **и** в разных стилях — при этом
> картинка красивая, а не просто технически корректная.

Опровержение так же ценно, как подтверждение: если идентичность рассыпается на
манхве, мы узнаём это за две недели, а не через полгода, и у нас остаются все
варианты — усилить контрольный стек, укоротить поводок, хранить стилевые
варианты ассета, пересмотреть подход к рендеру.

## 2. Ключевое: срез не блокируется решением 2.5

Открытое решение [2.5](Roadmap.md#2-представление-объекта-днк) (на чём базируем
структурированный латент) **не мешает начать**. MVP берёт готовый меш и обычный
рендер G-буфера — ни структурированные латенты, ни гауссианы, ни декодер здесь
не нужны.

Это сознательный размен: срез проверяет **риск на стороне генератора**, который
и есть главный продуктовый риск, не коммитясь к представлению объекта. Если
идентичность не переживёт стилизацию, вопрос о формате латента станет
неважным — падать будет нечему.

## 3. Что специально НЕ входит

| Не входит | Почему отложено |
| --------- | --------------- |
| Физика, разрушение, падение | Отдельный крупный риск; сценарий с посохом ломается от отсутствия персистентности раньше, чем от неточной физики. |
| Риг и смена позы | Ассет берём в одной готовой позе. Артикуляция — следующее утолщение. |
| Реестр ассетов, retrieval | Папка с одним файлом. |
| Парсинг промпта в граф сцены | JSON пишем руками. |
| Версионирование сцены, ветки | Не нужно, чтобы проверить гипотезу. |
| Структурированный латент, 3DGS | См. раздел 2. |
| Видео, темпоральная консистентность | Формат MVP — изображения. |
| Веб-сервис, очередь, UI | Скрипты и конфиги. |

## 4. Минимальный состав

### 4.1 Ассет — один персонаж

Готовый качественный 3D-персонаж (маркетплейс или собственная модель), не
сгенерированный. Убираем риск асcет-пайплайна из среза целиком: он проверяется
отдельно и позже.

**Требование к пропорциям — важное и неочевидное.** У аниме-персонажа голова,
глаза и пропорции тела отличаются от фотореалистичного человека. Если ассет
реалистичный, то «аниме» получится либо как реалистичный рендер с тун-шейдером
(не аниме), либо генератору придётся менять пропорции — а это ровно та свобода,
которая ломает геометрический замок идентичности.

Для MVP берём **промежуточные, полустилизованные пропорции** (уровень игрового
персонажа) и измеряем, насколько далеко один ассет растягивается в обе стороны.
Ответ определит, нужны ли стилевые варианты ассета
([Roadmap 7.7](Roadmap.md#7-рендер-стили-борьба-с-галлюцинациями)) и сколько.

### 4.2 Сцена

JSON руками: ссылка на ассет, камера (позиция, поворот, FOV), источники света.
Плюс простое окружение (земля, задник) — чтобы это была сцена, а не вырезанный
персонаж на сером фоне.

**Свет входит в MVP обязательно.** Если осветить плоско, мы получим скучные
картинки и сделаем неверный вывод «пайплайн выдаёт некрасиво», хотя на самом деле
мы просто плохо поставили свет. Минимум одна осмысленная световая схема.

### 4.3 Рендер G-буфера

Из обычного 3D-рендерера, набором проходов:

- глубина
- нормали
- маски инстансов по ID
- цвет (базовый рендер со светом)
- силуэт / контурные линии — понадобятся для стилизованных режимов

Плюс тот же кадр как быстрое превью (без генератора) — это уже второй тир
рендера из большой схемы, в зачаточном виде.

### 4.4 Стилевые конфигурации

Четыре стиля, но главное — что они отличаются **длиной поводка**, а не только
промптом. Это и есть основная настраиваемая сущность MVP:

| Стиль | Условия в генератор | Поводок | Комментарий |
| ----- | ------------------- | ------- | ----------- |
| Гиперреализм | глубина + нормали + маски + **цвет** | самый короткий | Генератор доводит материалы и оптику. Ожидаемо самый простой. |
| Кино | то же + свобода на грейдинг | короткий | Фотореализм плюс драматический свет и цветокоррекция. |
| Аниме | глубина + нормали + маски + контуры, **цвет снят** | длинный | Базой служит тун-рендер, генератор чистит и оживляет линию. |
| Манхва | то же, максимальная свобода подачи | самый длинный | **Главный риск MVP.** Проверяем первым после гиперреализма. |

Стилевые LoRA на старте берём готовые, не обучаем — обучение своих это
отдельная работа, и до неё надо сначала убедиться, что механизм в принципе жив.

### 4.5 Генератор

Диффузионный генератор в режиме img2img поверх рендера (не из шума), с
ControlNet-условиями по G-буферу. Выбор конкретной модели —
[Roadmap 7.11](Roadmap.md#7-рендер-стили-борьба-с-галлюцинациями); для MVP
критично только, чтобы лицензия допускала коммерческое использование.

### 4.6 Проверка

- **Счёт объектов и силуэт** — сошлось ли то, что в кадре, с тем, что в сцене.
- **Идентичность** — см. раздел 6, метрика частично открыта.
- Прогон всей матрицы одной командой, результаты в трекинг (`MLflow` уже есть).

## 5. Матрица эксперимента

Минимальный набор, который отвечает на вопрос:

|  | Гиперреализм | Кино | Аниме | Манхва |
| --- | --- | --- | --- | --- |
| Фас | ● | ● | ● | ● |
| Три четверти | ● | ● | ● | ● |
| Профиль | ● | ● | ● | ● |

Двенадцать изображений. Идентичность проверяется по строкам (один стиль, разные
ракурсы — легче) **и по столбцам** (один ракурс, разные стили — тяжелее). Второе
и есть настоящий тест.

## 6. Критерии успеха

| Критерий | Как меряем | Порог |
| -------- | ---------- | ----- |
| Идентичность по ракурсу | человеческая оценка «тот же персонаж?» внутри строки | ни одной неузнаваемой ячейки |
| Идентичность сквозь стиль | то же по столбцам матрицы | ни одной неузнаваемой ячейки |
| Соответствие стилю | человеческая оценка «это манхва / аниме / кино?» | стиль читается без подсказки |
| Отсутствие галлюцинаций | счёт объектов, лишние конечности, силуэт против рендера | ноль грубых нарушений |
| Красота | субъективная оценка | картинку не стыдно показать |

**Честная оговорка про метрику идентичности.** Автоматически измерить «тот же
персонаж» через пропасть фотореализм→манхва — само по себе нерешённая задача:
эмбеддинги, обученные на фотографиях, на стилизованном рисунке работают плохо.
Поэтому для MVP человеческая оценка — **основная**, автоматическая — справочная.
Разработка метрики уходит в [Roadmap 10.3](Roadmap.md#10-метрики-и-проверки).

## 7. Главный исследовательский вопрос MVP

> Насколько далеко **один** ассет растягивается по стилям, прежде чем ломается
> либо идентичность, либо качество стиля?

От ответа зависит крупное продуктовое решение: достаточно ли одного 3D-ассета на
персонажа, или база обязана хранить стилевые варианты — и тогда подготовка
контента дорожает кратно, а вместе с ней вся экономика
([Roadmap 4.3](Roadmap.md#4-поиск-и-наполнение-базы)).

## 8. Шаги

Каждый шаг имеет проверку; следующий не начинается, пока предыдущий не закрыт.

### S0 · Подготовить ассет `[ ]`
Выбрать и привести в порядок одного персонажа, полустилизованные пропорции,
одна поза. Плюс простое окружение и световая схема.
**Проверка ✅:** сцена открывается, рендерится, выглядит прилично без всякого генератора.

### S1 · Рендер G-буфера `[ ]`
Скрипт: сцена (JSON) → набор проходов (глубина, нормали, маски, цвет, контуры)
для заданного ракурса.
**Проверка ✅:** три ракурса, все проходы согласованы между собой; маски чистые на границах объектов.

### S2 · Сквозная цепочка, один стиль `[ ]`
Гиперреализм, один ракурс. Самый короткий поводок.
**Проверка ✅:** на выходе изображение, узнаваемо тот же персонаж, что в рендере.
**Если не прошло:** проблема не в стилизации, а в базовой связке — разбираться с условиями и силой денойза, дальше не идти.

### S3 · Три ракурса, тот же стиль `[ ]`
**Проверка ✅:** персонаж узнаётся во всех трёх ракурсах.
**Если не прошло:** геометрический замок не держит — усиливать контрольный стек, проверять чистоту масок.

### S4 · Манхва — главный риск `[ ]`
Снять цветовое условие, максимальная свобода подачи, три ракурса.
**Проверка ✅ (гейт MVP):** стиль читается как манхва **и** персонаж узнаётся во всех ячейках, включая сравнение с гиперреалистичным столбцом.
**Если не прошло:** это центральный результат среза. Развилки: хранить стилевые варианты ассета; удлинять поводок, но добавлять якорь идентичности (стилевой референс персонажа); признать, что стилевой разброс требует отдельного ассета на семейство стилей.

### S5 · Аниме и кино `[ ]`
Заполнить оставшиеся столбцы матрицы — они лежат между уже пройденными краями.
**Проверка ✅:** полная матрица 3×4 собрана.

### S6 · Второй объект в кадре `[ ]`
Добавить второй identity-несущий ассет рядом с персонажем.
**Проверка ✅:** атрибуты не перетекают — текстура одного объекта не оказывается на другом; оба узнаваемы.
**Если не прошло:** усиливать маскирование внимания по инстансам.

### S7 · Собрать в воспроизводимый прогон `[ ]`
Одна команда → вся матрица → изображения и метрики в трекинг.
**Проверка ✅:** повторный прогон того же конфига даёт тот же результат; матрица становится регресс-набором для всех последующих утолщений.

## 9. Открытые вопросы внутри MVP

| Вопрос | Почему важен |
| ------ | ------------ |
| Какие исходные пропорции ассета брать за базу | Определяет, в какую сторону тянуть стили и нужны ли варианты (см. 4.1, 7). |
| Готовые стилевые LoRA или обучать свои | Готовые быстрее, но могут тянуть чужую идентичность в лицо персонажа. |
| Чем анкерить идентичность в стилизованных режимах, если геометрии мало | В гиперреализме идентичность держится отрендеренным цветом; в манхве этого источника нет. |
| Как чисто получить маски инстансов на границах | Грязная маска ломает весь контрольный стек. |
| Сколько ракурсов достаточно | Три — минимум; крайние ракурсы (сверху, со спины) могут ломаться раньше. |

## 10. Что дальше, после среза

Утолщать по данным, а не по плану: следующим делается тот слой, который
оказался слабым звеном для нужной возможности. Наиболее вероятный порядок —
второй персонаж и реестр ассетов, затем поза и риг, затем хранилище сцены с
инкрементальными правками, и только потом физика. Матрица из S7 остаётся
регресс-набором: каждое утолщение обязано её не сломать.
