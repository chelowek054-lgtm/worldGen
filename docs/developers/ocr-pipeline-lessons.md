# Уроки pet-проекта OCR (CRNN): паттерны ML-пайплайна

Конспект практических решений из отдельного pet-проекта — распознавание автономеров
(CRNN + CTC на PyTorch, MLflow-трекинг). Проект не входит в этот репозиторий, исходники
лежали в `D:\Tests`. Здесь — то, что применимо к `engine/` при развитии фаз 0.1–0.2
(золотой набор, метрики, воспроизводимость) и далее.

## Стек

- PyTorch, `albumentations` (аугментации + `ToTensorV2`), `Pillow`.
- MLflow (SQLite-бэкенд) — трекинг параметров, метрик по эпохам, артефактов.
- `python-Levenshtein` / `RapidFuzz` — метрики расстояния редактирования.
- Hydra в этом проекте не использовался (плоский `config.yaml` + `yaml.safe_load`) —
  в `engine/` уже сделано лучше через Hydra-конфиги, откатываться не нужно.

## Структура кода

Монолит был осознанно разнесён на модули (аналогично `engine/worldgen/`):

```
core/
  model.py             # архитектура (CRNNModel)
  dataset.py            # PyTorch Dataset + аугментации
  trainer.py             # цикл обучения
  predictor.py            # инференс-класс, batch-инференс
  metrics.py               # Exact Match / CER / char_acc
  checkpoints_store.py       # сохранение/загрузка чекпоинтов
```

Вывод: `model` / `dataset` / `trainer` / `predictor` / `metrics` как отдельные модули —
рабочее разделение ответственности для ML-пайплайна, стоит держать тот же принцип
в `engine/worldgen/` по мере роста (сейчас там `seed.py`, `paths.py`, `tracking/`, `eval/`).

## Работа с данными — что стоит переносить на золотой набор (`0.1b`)

Из фазы очистки данных (актуально при наполнении `engine/data/golden_set/`):

- **MD5-дедупликация до сплита.** Полные бинарные дубликаты, попавшие одновременно
  в train/val (или в золотой набор), искусственно завышают метрики. Хешировать и
  вычищать *до* любого разбиения.
- **Фильтрация по геометрии.** Отсекать аномальные размеры/aspect ratio, а не
  полагаться на то, что модель «сама разберётся» — на границе распределения данные
  обычно шумные, а не информативные.
- **Валидировать данные под конкретный алгоритм.** В CTC это условие `T > L`
  (число временных шагов сети должно превышать длину целевой строки) — при нарушении
  `CTCLoss` не проходит выравнивание. Для наших метрик оси A/B (DINO-косинус,
  RAFT warp-error и т.д.) нужен свой аналогичный чек на входе, а не падение в рантайме.
- **Логировать брак с причиной.** Все отфильтрованные сэмплы — в отдельный файл
  (`anomalies.csv`) с колонкой причины (`duplicate_md5_hash`, `bad_aspect`, …). Это
  сразу даёт аудит золотого набора и объясняет расхождения в размере выборки.
- **Честный сплит по сложности, не только по индексу.** Здесь сплит делался по длине
  текста, чтобы train/val имели одинаковое распределение сложности. Для мультивидовых
  данных (фаза 1.1) аналог — не пускать одну и ту же сцену/объект в разные сплиты.
- **Нормализация меток до токенизации.** Здесь — обязательный `.upper()`; смешанный
  регистр в сырых метках раздувал алфавит и путал модель. Общий принцип: нормализация —
  явный шаг пайплайна, а не «модель разберётся».

## Обучение и трекинг

- MLflow: логировать **плоский** конфиг (`flatten_dict` вложенного YAML), метрики
  по эпохам и финальные артефакты (лучшие веса) — тот же паттерн уже есть в
  `engine/worldgen/tracking/`, здесь просто рабочее подтверждение, что он окупается
  на практике (быстро находить регрессии между запусками).
  а трекер должен быть выключаем в один параметр — тоже уже сделано (`tracking=noop`).
- Планка обучения: `AdamW(weight_decay=1e-4)` вместо простого `Adam`, плюс
  `ReduceLROnPlateau(patience=3, factor=0.5, mode='max')`, отслеживающий *целевую*
  метрику (Exact Match), а не loss — вышли из плато на ~82% Exact Match.

## Метрики качества строки/последовательности

Реализация в `core/metrics.py` — минимальный набор без внешних зависимостей:

- **Exact Match** — доля полных совпадений строки.
- **CER** (`total_edit_distance / total_target_len`) — нормализовано на весь корпус,
  не усреднение по сэмплам.
- **Char accuracy** = `1 - normalized_edit_distance` (Левенштейн, нормализованный на
  `max(len(pred), len(target))` для каждого сэмпла).

Пригодится как референс при реализации метрик оси A/B в `0.2`/`0.3` — не обязательно
тянуть тяжёлые библиотеки под простые edit-distance метрики.

## Confidence score — геометрическое среднее, не арифметическое

Формула уверенности для целой последовательности символов: экспонента среднего
логарифмов вероятностей = геометрическое среднее = произведение вероятностей всех
`N` финальных символов (после CTC-декодирования, без `blank`/дублей), извлечённое
в степени `1/N`.

Почему не арифметическое среднее:

- **Корень `N`-й степени убирает штраф за длину** — иначе длинные последовательности
  систематически получают более низкий score, даже при равной уверенности по символу.
- **Жёстче штрафует за один слабый символ.** Арифметическое среднее сглаживает одну
  грубую ошибку; геометрическое — резко просаживает общий балл.
  Пример: `(0.99, 0.10)` → арифметическое `0.545` (маскирует проблему),
  геометрическое `√(0.99·0.10) ≈ 0.31` (сразу видно).

Применимо к любой задаче, где итоговый score строится по последовательности токенов
с разной длиной между сэмплами (не только OCR) — стоит иметь в виду при проектировании
скалярных метрик уверенности для оси A/B.

## Инференс

- Отдельный `Predictor`-класс, не завязанный на train-код: принимает путь/`PIL.Image`/
  `np.ndarray`, сам нормализует вход (`RGB`, grayscale→RGB, RGBA→RGB), грузит алфавит
  из чекпоинта (а не из текущего конфига) — воспроизводимость инференса не зависит от
  того, что лежит в `config.yaml` на момент запуска.
- Батчевый инференс с явным замером CPU/GPU (в этом проекте — ~14.6× спидап на
  RTX 4050 CUDA vs CPU) — полезная привычка для бенчмарков движка на разных бэкендах.

## Типичные паттерны ошибок (полезно как чек-лист для разбора ошибок)

- Наибольшая доля ошибок — не «модель не видит объект», а форматирование
  (пробелы/разделители: пропуски и лишние вставки).
- Похожие по начертанию символы путаются предсказуемо (`O`/`0`, `3`/`7`/`8`) —
  и конфликт алфавитов (кириллица/латиница похожих букв) — стоит закладывать в
  анализ ошибок заранее, а не удивляться постфактум.
- Обрезка краёв последовательности — частый сбой на границе (потеря крайних
  цифр/символов), стоит явно проверять на выборке worst-case примеров, а не только
  на агрегированной метрике.
